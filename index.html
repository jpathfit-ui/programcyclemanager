      How the Automated Parts of This App Work

      A plain-language map of every piece of logic that runs on its own — what triggers it, what it actually does, and which real workbook mechanism it mirrors. Nothing here is a config value; it's documentation of behavior.

      1. Three-Layer Architecture

      Same split as the workbook: tables are the only source of truth (RAW, DECISIONS, AMENDMENTS, WAITLIST, EQUITY, VENDOR_MAP), derived views are always recomputed from tables rather than hand-edited (NORMALIZED, COMPETITION_ROWS, live equity status, budget totals), and actions are the only things allowed to write to a table (Auto-Resolve, Confirm Suggestion, the four Mid-Cycle Changes forms). Nothing in this app edits a derived view directly — if a number looks wrong, the fix always happens at the table level, then everything downstream recomputes.

      2. Dual-Cycle Resolution

      Decision_Active and Operations_Active are independent flags on tblCycleRules — a cycle can be operational while a different cycle is still taking decisions. GetDecisionCycle() and GetOperationsCycle() resolve which cycle each one is, and nothing else hardcodes a cycle name. When amending an existing decision, the cycle used is whichever cycle that specific decision actually belongs to (GetCycleForDecisionRow()) — except Add New, which has no prior row to inherit from and falls back to the decision cycle (GetActiveCycleOrWarn()). Switching the decision cycle in Settings resets the Approval Queue pipeline, since everything in it was scoped to the cycle that just changed.

      3. Normalization (Table → Query)

      Raw FormExport rows are wide (one column per program, mostly blank). Normalize unpivots each non-blank cell into its own row, then parses the slot text (e.g. "MAP Monday 11:00-12:00") into Program_Label, Day, Start, End. Only rows tagged with the current GetDecisionCycle() are processed — a different cycle's imported data sits inactive until that cycle opens for decisions.

      4. Competition Detection

      Normalized requests are grouped by Slot_Key. One unit requesting a slot → Clean, auto-approved with method "No Competition". Two or more units requesting the same slot → Competing, routed to equity-informed suggestion instead of auto-approval.

      5. Equity-Informed Suggestions

      For each competing slot, the unit with the most negative Variance (Approved − Target — i.e. most under-served) is suggested. When two or more units are exactly tied, nothing is auto-decided — it's flagged for manual review rather than guessed. Equity numbers are live: every confirmed decision recalculates Approved, Variance, Status, and Fulfillment Rate for that unit immediately, everywhere in the app (chips, suggestions, Settings). Requested/Minimum/Target stay as policy inputs and don't move on their own.

      6. Waitlist Logging

      Whenever a competing slot is resolved (suggestion confirmed or a tie manually broken), every unit that did not win is automatically logged with reason "Lost Contested Slot" — mirrors tblWaitlistLog. This happens without any manual step; it's a side effect of confirming a decision, not a separate action.

      7. Cost & Budget Calculation

      Mirrors qCycleCost. Every approved decision recurs weekly for the full cycle, so cost is Rate × CycleWeeks per billable unit of demand — but "billable unit" means something different depending on the vendor's Rate_Type:

      Session vendors (most vendors): each distinct approved session is billed once per week of the cycle. If a program is shared across multiple units for the same slot, only the first unit counts as billable (Cost_Count = 1); every other sharing unit gets equity credit for it but isn't billed again (Cost_Count = 0) — this app applies that dedup at budget-calculation time using the Shared Unit Slot Keys list in Policy Constraints, rather than at the moment a decision is written.

      Day-rate vendors (e.g. Smile Theatre, Sunshine Garden, Top Rail Stables): billed per day the vendor is on-site, not per session and not per unit — three units seeing the same day-rate vendor on the same day is still one day's pay. Dedup here is by unique (Vendor, Day) pair across every unit's approved decisions for that vendor, not by session.

      8. Fuzzy Search (Mid-Cycle Changes)

      Mirrors FuzzySearchDecisionKey: your search is split into individual words, and all of them must appear somewhere in that decision's combined Slot Key + Unit + Vendor text (an AND match across terms, not an OR). A confirmed Cancel removes that decision from the searchable pool immediately; a confirmed Add New (once marked Confirmed, not while still Pending) adds a new one — both live, both immediate.

      Secondary Offers

      Session vendors only — this pass requires extra funds to fill vendor availability. Offers open slots to two candidate buckets, tracks Yes/No replies, and processes everything in one batch at a deadline you set, first-come-first-served with a live equity tiebreak. Every offer is flagged against remaining budget headroom, so you never approve one without knowing it fits. Day-rate vendors are handled separately by the Day Rate Pass — those don't require additional budget to fill open slots (the vendor is already on-site).
